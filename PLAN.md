# Plan.md: micro-MVP «Кто выгуливает Бориса»

## 1. Текущий статус

- Приоритет: главный сценарий — запись на прогулку в один из пяти слотов с серверной защитой от двойной записи и хранением в SQLite.
- Текущее состояние: приложение реализовано: сервер на Node.js, SQLite, страница со слотами и карточкой кормления. Автоматическая проверка в браузере пройдена, README обновлён. Остался ручной smoke-check.
- Основная цель цикла: рабочая локальная страница, которая проходит все семь DoD и smoke-check из `spec.md`.
- Обязательные ограничения: только Node.js + npm + SQLite по схеме из `spec.md`; без `localStorage`, моков и состояния в памяти; без авторизации, отмены записи, календаря, уведомлений, интеграций и деплоя; только синтетические ФИО; одна задача за итерацию.
- Основной контекст проекта: `spec.md` (контракт), `AGENTS.md` (правила агента), `README.md`, `PLAN.md`.
- Текущий активный шаг: 6 — ручной smoke-check.

## 1.1 Целевой сценарий

1. Сотрудник открывает общую страницу без авторизации.
2. Видит текущую дату и пять слотов: `09:00`, `11:00`, `13:00`, `15:00`, `17:00`.
3. Выбирает свободный слот и вводит имя и фамилию.
4. Подтверждает запись — слот становится занятым и показывает имя.
5. Другой сотрудник пытается занять тот же слот и получает понятный отказ от сервера. Исходная запись не меняется.
6. После обновления страницы или открытия во втором браузере состояние то же.
7. Дополнительно: сотрудник видит карточку «Последнее кормление» (дата, время, имя), вводит имя, нажимает «Покормили Бориса», и карточка обновляется.

## 2. Требования к результату

- `spec.md` — единственный источник продуктовых требований. При реализации не меняется.
- `README.md` — после последней принятой правки описывает фактические команды запуска, адрес, структуру файлов, сценарий и границы.
- `AGENTS.md` — правила агента, при реализации не меняются.
- `PLAN.md` — после каждой принятой правки отмечен статус шага и фактический результат проверки.
- Границы этапа: только функции из `spec.md`. Кормление — небольшая дополнительная карточка, а не второй пользовательский поток.

## 3. Что делаем по шагам

- [x] 1. Каркас Node.js-проекта и SQLite
  - Действие: создать минимальный Node.js-проект с запуском через `npm start`, установить SQLite-драйвер, создать таблицы `walk_slots` и `feedings` по схеме из `spec.md`, при старте создавать пять свободных слотов на текущую дату, если их ещё нет.
  - Результат: `package.json`, `server.js`. Используется встроенный `node:sqlite`, сторонний драйвер не понадобился. База `boris.sqlite` создаётся при первом запуске, слоты на день — через `INSERT OR IGNORE`.
  - Проверка: `npm start` запускается без ошибок; в базе ровно пять слотов на текущую дату, все свободны; повторный запуск не создаёт дубликатов.
  - Факт: на пустой базе `GET /api/state` вернул пять свободных слотов; после перезапуска сервера в `walk_slots` по-прежнему 5 строк, записи сохранились.

- [x] 2. Серверное API слотов с атомарной записью
  - Действие: добавить получение слотов на текущую дату и запись на слот по ФИО. Запись — одна атомарная операция `UPDATE ... WHERE booked_by IS NULL` или транзакция; ФИО обрезается по краям и не может быть пустым.
  - Результат: `GET /api/state`, `POST /api/slots/book`. Запись — один `UPDATE ... WHERE booked_by IS NULL`; если ни одна строка не изменилась, сервер отвечает `409` с именем того, кто уже записан.
  - Проверка: два запроса подряд на один слот — первый успешен, второй получает конфликт, в базе осталось первое ФИО (DoD 4).
  - Факт: первый запрос — `200`, второй — `409` «Слот 11:00 уже занят: с Борисом гуляет Анна Тестова. Выберите другое время». Пять параллельных запросов на один слот — один `200`, четыре `409`. Пустое имя — `400`, несуществующий слот — `404`.

- [x] 3. Страница со слотами
  - Действие: сделать одну страницу, которая показывает текущую дату и пять слотов, визуально различает свободные и занятые, для свободного даёт ввести ФИО и записаться, для занятого показывает ФИО без кнопки записи, а ошибку конфликта выводит понятным текстом.
  - Результат: `public/index.html`, `public/style.css`, `public/app.js`. Пиксельный стиль: светлый фон, текст `#333333`, синий акцент, шрифты Handjet и IBM Plex Mono, без капса, неразрывные пробелы по правилам типографики. Занятый слот — штриховка, зачёркнутое время и «Гуляет: имя», выбрать его нельзя.
  - Проверка: запись «Анна Тестова» в свободный слот — слот занят и показывает ФИО; после обновления страницы и во втором браузере состояние сохраняется (DoD 1, 2, 3, 5).
  - Факт: автоматическая проверка в headless Chrome — дата и пять слотов на месте, запись проходит, вторая вкладка видит запись, при конфликте показывается отказ сервера и список обновляется, после обновления страницы состояние сохраняется.

- [x] 4. Карточка «Последнее кормление»

  - Результат: `POST /api/feedings`. Карточка показывает «Сегодня, 15:09 • Илья Примеров» («Вчера, …» или «21 октября, …» для прошлых дней), без отметок — «Пока нет отметок». Справа поле «Ваши имя и фамилия» и кнопка «Покормили Бориса», прижатые к нижней границе.
  - Проверка: отметить кормление «Илья Примеров» — карточка показывает новое время и ФИО, после обновления страницы данные сохраняются (DoD 6).
  - Факт: после отметки карточка показала «Сегодня, 14:25 • Илья Примеров»; после обновления страницы и перезапуска сервера данные на месте.
